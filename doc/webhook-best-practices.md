Webhook Signature Verification &amp; Security\n\n### 🔴 GAP: No webhook authenticity verification in current code\n\n**What Telegram provides:**\n- **`secret_token` parameter** in `setWebhook`: When specified, Telegram sends header `X-Telegram-Bot-Api-Secret-Token` with the secret value.\n- **Secret path** (legacy): Append a unique token to the webhook URL. Only Telegram knows it.\n\n**Recommendation: HIGH PRIORITY — add secret_token verification**\n```typescript\n// In src/webhook.ts or app.ts route handler:\napp.post('/webhook/bot/:botId', async (c) =&gt; {\n  const secretFromTelegram = c.req.header('X-Telegram-Bot-Api-Secret-Token');\n  const expectedSecret = process.env.WEBHOOK_SECRET;\n  \n  if (expectedSecret &amp;&amp; secretFromTelegram !== expectedSecret) {\n    return c.json({ error: 'Forbidden' }, 403);\n  }\n  // ... proceed with webhook handling\n});\n```\n\n**Notes:**\n- The `WEBHOOK_SECRET` env var already exists in `.env.example` but is NOT used.\n- Use constant-time comparison (`crypto.timingSafeCompare`) to prevent timing attacks.\n- Telegram's Bot API docs confirm: \"If you'd like to make sure that the webhook was set by you, you can specify `secret_data` in the parameter `secret_token`.\"\n\n### ⚠️ Webhook URL considerations\n- Railway provides HTTPS automatically → no self-signed cert needed.\n- Supported webhook ports: 443, 80, 88, 8443. Railway routing handles this transparently.\n- Redirections are NOT supported by Telegram; ensure your webhook URL lands directly on the app.\n\n---\n\n## 2. Telegram Bot API Rate Limits\n\n### Official Limits (from core.telegram.org/bots/faq)\n\n| Scenario | Limit | Current Code Impact |\n|---|---|---|\n| **Single chat** | 1 message per second | ⚠️ Admin `sendMessage` calls need throttling |\n| **Group chat** | 20 messages per minute | ⚠️ Need rate limit tracking in gateway |\n| **Bulk broadcast** | ~30 messages per second (free) | ❌ No throttle layer;\na\n **Paid broadcasts:** up to 1,000 msg/s with Telegram Stars | Paid broadcasts require 10k+ monthly active users + 10k+ Star balance |\n\n### 🔴 GAP: No rate limiting on outgoing bot API calls\n\nThe admin API (`src/admin.ts`) makes Bot API calls (sendMessage, editMessageText, etc.) without any rate limiting. On a multi-bot setup with many concurrent clients:\n- A single client could trigger 100+ sendMessage calls rapidly → flooding Telegram's rate limiter with 429 errors.\n- Redis Pub/Sub fanout in multi-replica mode amplifies this: every replica processes every update independently.\n\n### Recommendation: Implement a per-bot TokenBucket rate limiter**\n```typescript\nimport { createTokenBucket } from 'some-rate-limiter-lib';\n// or implement manually:\nclass BotRateLimiter {\n  private buckets = new Map&lt;string, { remaining: number; lastRefill: number &gt;();\n\n  consume(botId: string): boolean {\n    const now = Date.now();\n    const bucket = this.buckets.get(botId) || { remaining: 30, lastRefill: now };\n    \n    // Token bucket refills at 30/sec (global broadcast limit)\n    elapsed = (now - bucket.lastRefill) / 1000;\n    const refill = elapsed * 30;\n    bucket.remaining = Math.min(30, remaining + refill);\n    bucket.lastRefill = now;\n\n    if (bucket.remaining >= 1) {\n      bucket.remaining -= 1;\nthis.buckets.set(botId); // Store bucket in a shared store per replica for multi-replica consistency. Use Redis Lua script `INCR` with TTL for cross-replica atomic counting.\n      return true;\n    }\n    return false;\n  }\n}\n```\n\n**Next to coder:**\n- Add rate limit middleware around all admin API routes in `src/admin.ts`.\n- Use per-bucket token-based approach (30 tokens/sec default, configurable per bot).\n- On 429 from Telegram: log warning with retry_after value, queue the message for later retry.\n\n---\n\n## 3. Error Handling Patterns\n\n### A. 429 Rate Limit Errors (Telegram side)\n**From JavaThinking.com research:**\n- Telegram returns: `{ ok: false, error_code: 429, description: \"Too Many Requests: retry after X\" }`\n- `X` is in **seconds** — always use this exact value as the wait delay.\n- Retry strategy: exponential backoff starting at ~1 second (or use the retry_after value from Telegram).\n\n```typescript\n// Recommended retry pattern for outgoing Bot API calls:\nasync function sendMessageWithRetry(botId, chatId, text, maxRetries = 3) {\n  for (let i = 0; i < maxRetries; i++) {\n    const res = await fetch(`https://api.telegram.org/bot${botConfig.token}/sendMessage`, {\n      method: 'POST',\n      body: JSON.stringify({ chat_id: chatId, text }),\n    });\n\n    if (res.ok) return true;\n    \n    const body = await res.json();\n    if (body.error_code === 429) {\n      const retryAfter = body.parameters?.retry_after || (1 * Math.pow(2, i));\n      await new Promise(r =&gt; setTimeout(r, retryAfter * 1000));\n      continue;\n    }\n    \n    // Non-retryable error — fail fast\n    return false;\n  }\n  return false; // Exhausted retries\n}\n```\n**Note:** Use `retry_after` from Telegram **first**, backoff only if unavailable.\n\n### B. Webhook Delivery Failures (Telegram → Gateway)\n- Telegram retries failed webhook deliveries for ~1 day (exponential backoff).\n- Current code: returns plain `\"OK\"` text — acceptable, but should log failures for monitoring.\n- **Recommendation: Add logging for response codes**\n```typescript\napp.post('/webhook/bot/:botId', async (c) =&gt; {\n  try {\n    // ... webhook handling\n    c.header('Content-Type', 'text/plain');\n    return c.text('OK');\n  } catch (err) {\n    console.error(`[webhook] Bot ${botId} failed:`, err);\n    c.status(500);\n    return c.text('INTERNAL SERVER ERROR');\n  }\n});\n```\n\n### C. Bot Token Validation Errors (on register)\n**Current code in `admin.ts`:** Makes a raw `fetch(getMe)` call with no timeout — vulnerable to hanging.\n- **Add timeout** (5-second fetch with AbortController).\n- **Log descriptive errors:** \"Invalid token format\", \"Bot already exists\", etc.\n- **Return structured error responses** for common failure modes:\n  - Invalid/empty token → HTTP 400 + `{ error: 'invalid_token' }`\n  - Token not a bot → HTTP 400 + `{ error: 'not_a_bot' }`\n  - Network timeout → HTTP 503 + `{ error: 'timeout' }`\n\n### D. WebSocket Client Errors\n- **Unhandled disconnections:** Current gateway doesn't track disconnect events (only messages). Add `ws.on('close', ...)` to clean up subscriptions and unsubscribe from Redis Pub/Sub channels.\n- **Connection pool exhaustion:** No limit on max WS connections per client. Currently unlimited — add a `SUBSCRIPTION_MAX_PER_CLIENT` enforcement (already env var exists but not enforced in gateway.ts).\n\n---\n\n## 4. WebSocket Scaling: Redis Pub/Sub Validation\n\n### Existing Research (`doc/multi-replica.md`) — Status: ✅ SOLID FOUNDATION\n\nThe multi-replica recommendation is well-researched and sound:\n- Uses Redis Pub/Sub for at-most-once delivery (acceptable for real-time fanout)。\na\n **Next steps needed before implementation:**\n1. Choose between `ioredis` or `redis` (modern, native ESM package — lighter).\n2. Use channel pattern `telegram:update:{botId}` with fine-grained subscription only for active bots (avoid subscribing to `*` wildcard which floods all messages through every replica).\n3. Add a `source_instance_id` field to prevent echo loops.\n4. **Critical addition not in multi-replica.md: Redis connection health monitoring** — on Redis disconnect, degrade gracefully (local-only broadcasting) and log with severity.\n5. Consider Redis Streams if at-least-once delivery becomes a requirement later. Pub/Sub is sufficient for now.\n\n### ⚠️ Scaling concern: Update payload size\n- Telegram updates can include photos, videos, documents up to **50 MB** (per Bot API docs).\n- Broadcasting full update payloads via Redis would be wasteful and could cause memory pressure.\n- **Recommendation: Only broadcast essential fields** in Redis messages — filter out large binary payloads:\n```typescript\n// Instead of sending the full update object,\n// send only what's needed for client reconstraction:\n{\n  source: instanceId,\n  botId,\n  timestamp: Date.now(),\n  message?: { chat_id, text, entities, reply_markup? }, // flattened\n  // Omit: file_ids (clients fetch via getMe separately), photos[], video[], etc.\n}\n```\n\n---\n\n## 5.
