# Multi-Replica WebSocket Synchronization Recommendation\n\n## Problem\n\nThe current architecture uses an in-memory `Map` to store WebSocket subscriptions per bot ID (`src/gateway.ts`). When scaling to multiple Railway replicas (containers/pods), an incoming Telegram webhook handled by one replica cannot forward the update to WebSocket clients connected to other replicas. This results in message loss unless sticky sessions are used, which is not ideal for WebSockets as connections are long-lived and load balancers may distribute new connections arbitrarily.\n\n## Solution: Redis Pub/Sub Message Bus\n\nUse a shared Redis instance as a lightweight message bus to broadcast updates from the instance that receives a webhook to all other replicas.\n\n### How It Works\n1. **Local Subscription Map**: Each replica maintains a local `Map<botId, Set<WebSocket>>` for its connected WebSocket clients.\n2. **Webhook Handling**: When a replica receives a Telegram webhook for `botId`, it:\n   - Broadcasts the update to its local subscribed clients (fast path).\n   - Publishes a message to a Redis channel `telegram:update:{botId}` with the update payload and a source instance identifier.\n3. **Redis Subscription**: All replicas are subscribed to the pattern `telegram:update:*` (or individual bot channels).\n4. **Remote Update Handling**: When a replica receives a message from Redis for a bot ID:\n   - Checks the source instance ID; if it matches the local replica, ignores the message (to avoid echo).\n   - Otherwise, broadcasts the update to its local subscribed clients for that bot ID.\n\n### Implementation Details\n\n#### Redis Client Setup\n- Use the `ioredis` or `redis` Node.js client.\n- Create a single Redis client per replica (connection pooling handled by the client).\n- Connect using the `REDIS_URL` environment variable provided by Railway when adding a Redis service.\n\n#### Message Format\n```json\n{\n  \"source\": \"<instance-id>\",\n  \"botId\": \"<bot-id>\",\n  \"update\": <telegram-update-object>,\n  \"timestamp\": <unix-ms>\n}\n```\n\n- `source`: Unique identifier for the replica (e.g., `process.env.HOSTNAME` or a UUID generated at startup).\n- `botId`: The Telegram bot ID the update is for.\n- `update`: The raw Telegram update object (as received from Telegraf).\n- `timestamp`: Optional, for debugging and latency measurement.\n\n#### Deduplication\n- Prevent a replica from processing its own published updates via the `source` field.\n- Alternative: Use Redis `RESP3` client tracking to ignore messages from the same connection, but source ID is simpler and works across connections.\n\n#### Subscription & Unsubscription\n- No changes needed to WebSocket subscription logic; subscriptions remain local per replica.\n- When a client subscribes/unsubscribes to a bot ID, update the local `Map` only.\n\n#### Reliability & Fault Tolerance\n- **Message Loss**: Redis Pub/Sub offers at-most-once delivery; if a replica is temporarily offline, it may miss updates published during that downtime. This is acceptable for real-time Telegram updates where occasional loss is tolerable (Telegram may resend via getUpdates long polling as a fallback, but we rely solely on webhooks).\n- **Recovery**: On reconnect, the replica resumes listening for new updates; missed updates are not recovered (by design). If stricter guarantees are needed, consider Redis Streams with consumer groups (see \"Advanced Option\" below).\n- **Redis Failure**: If Redis is unavailable, updates will not propagate across replicas. Local webhook handling still works (clients connected to the same replica receive updates). Consider implementing a fallback to local-only broadcasting with degraded performance metrics logged.\n\n#### Performance Considerations\n- Each update incurs one Redis `PUBLISH` and (N-1) `SUBSCRIBE` messages where N is the number of replicas.\n- Latency: Typically sub-millisecond within the same Redis instance (likely same region).\n- Scaling: Horizontal scaling of replicas increases Pub/Sub traffic linearly; monitor Redis bandwidth and CPU.\n- Connection Overhead: Each replica maintains a persistent Redis connection; negligible.\n\n### Advanced Option: Redis Streams for At-Least-Once Delivery\n\nIf the application cannot tolerate lost updates, replace Pub/Sub with Redis Streams:\n- Each webhook results in an `XADD` to a stream `telegram:stream:{botId}`.\n- Each replica consumes the stream using a consumer group (one group per replica, unique consumer name).\n- Guarantees that each update is processed by at least one replica (though in this case we want *all* replicas to process it for local fanout).\n   → Actually, for fanout to all replicas, we need each replica to receive every update. Streams with consumer groups are for competing consumers; not ideal.\n- Alternative: Use a single stream and have each replica read all entries using `LAST_ID` saved per replica (more complex).\n\nGiven the use case (real-time WebSocket fanout), Pub/Sub is sufficient and simpler.\n\n### Railway Integration\n\n1. **Add Redis Service**:\n   - In Railway dashboard, add a Redis service (or use the Railway Redis template).\n   - The service will provide a `REDIS_URL` environment variable automatically.\n2. **Update `package.json`**:\n   - Add dependency: `ioredis` (or `redis`).\n3. **Initialize Redis Client** (e.g., in `src/gateway.ts` or a dedicated `src/redis.ts`):\n   ```typescript\n   import Redis from 'ioredis';\n   const redis = new Redis(process.env.REDIS_URL);\n   export { redis };\n   ```\n4. **Modify Webhook Handler** (`src/webhook.ts`):\n   - After processing the update locally, publish to Redis.\n5. **Modify Gateway** (`src/gateway.ts`):\n   - On initialization, subscribe to Redis pattern `telegram:update:*`.\n   - Handle incoming messages as described.\n6. **Environment Variable**:\n   - Add `REDIS_URL` to Railway variables (automatically set when Redis service is linked).\n7. **Health Check**:\n   - Add a Redis ping to health endpoint to detect connectivity issues.\n\n### Trade-offs & Alternatives\n\n| Approach          | Pros                                      | Cons                                      | Verdict                     |\n|-------------------|-------------------------------------------|-------------------------------------------|-----------------------------|\n| Redis Pub/Sub     | Simple, low latency, easy to implement    | At-most-once delivery (possible loss)     | **Recommended**             |\n| Redis Streams     | Persistent, replayable, consumer groups   | More complex; overkill for fanout         | Consider if loss unacceptable |\n| Shared DB (Postgres) | ACID, familiar                           | Higher latency, overkill                  | Not recommended             |\n| Socket.io + Redis Adapter | Built-in scaling, rooms                | Adds socket.io dependency; larger bundle | Evaluate if using socket.io |\n| Railway-native    | No external service                       | Not available for WebSocket fanout        | N/A                         |\n\n### Recommendation\n\nImplement Redis Pub/Sub as described. It provides a scalable, low-latency solution for multi-replica WebSocket update distribution with minimal changes to the existing codebase. Monitor Redis metrics and consider upgrading to a higher tier if Pub/Sub traffic becomes a bottleneck.\n\n## Next Steps\n\n1. Add Redis service to Railway project.\n2.
