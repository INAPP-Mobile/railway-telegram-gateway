# `cowork-railway` Extension: Variables Management\n\n## Goal\nAllow agents to manage Railway environment variables programmatically via the existing `cowork-railway` tool, eliminating UI/manual CLI steps for first-time setup and env var validation.\n\n## Current State\n- `cowork-railway` (status) checks project/service health.\n- `cowork-railway-deploy` handles deployment but requires manual env var config in dashboard.\n- No way to push variables from code/agent context to Railway.\n\n---\n\n## Proposed Extension: New `vars` Subcommand/Action\n\nAdd a new action to the existing `cowork-railway-deploy` (or separate endpoint) called `vars` with these operations:\n\n### Operations\n| `op` | Description |\n|------|-------------|\n| `set` | Set specific key-value pairs in a Railway environment (production/staging). |\n| `list` | List current env vars for the project, flagged against `.env.example`. Shows missing required vs missing optional vars. |\n| `push` | Read `.env.example` → check which keys are already set via API → push only unset keys to the target environment. Optionally skips optional vars or prompts user. |\n| `validate` | Check if all *required* variables are configured in production. Returns pass/fail with missing var list. |\n\n### Parameters\n| Parameter | Type | Description |\n|-----------|------|-------------|\n| `op` | string | One of: `set`, `list`, `push`, `validate` |\n| `name=value,foo=bar` | string | Key-value pairs for `set`. Pass as comma-separated or JSON object. |\n| `env` | string | Target environment (`production` default, also supports `staging`) |\n| `projectOrServiceId` | string | Optional explicit target if multiple projects exist |\n\n---\n\n## Implementation Requirements (Coder)\n\n1. **Authentication**:\n   - The PM/tool needs a way to authenticate with Railway. We have two options:\n     - Option A: User provides their Railway API Token via `.cowork/settings.json` → `settings.railway.apiKey = \"rv1_...\"`.\n     - Option B: Tool reads `~/.railway/authenticated-accounts.yaml` if the user has run `railway auth login` locally. (Recommended for simplicity — no new config needed if they're already logged in).\n2. **API Calls**:\n   - Use Railway REST API to read/update variables.\n     - List/Get vars: `GET https://api.railway.app/api/v2/service/{serviceId}/settings`\n     - Update var: `PATCH https://api.railway.app/api/v2/variable/{variableId}`\n     - Create var: `POST https://api.railway.app/api/v2/environment/{environmentId}/variables`\n3. **Logic for `push`**:\n   - Read `.env.example`, extract only variable names.\n   - Fetch current project settings via API.\n   - Compare lists → identify missing variables (required + optional).\n   - For each missing var, check if it has a non-empty default in `.env.example`. If so, push with that value + a comment like `Set by railway-vars tool — update this value!`.\n   - Skip vars that are explicitly meant to be secrets (those without defaults) unless user provides explicit values via `op=set` or passes the `-i` flag for interactive prompt fallback.\n4. **Logic for `validate`**:\n   - Fetch current project settings → return list of missing required variables (those marked as required in `.env.example`).\n\n---\n\n## Acceptance Criteria\n- [ ] Tool exists and is callable from within any agent session.\n- [ ] `vars set name=value,foo=bar` writes to production env reliably.\n- [ ] `vars list` flags vars against `.env.example` + source of truth.\n- [ ] `vars push` correctly diffs local `.env.example` → remote and pushes only missing keys.\n- [ ] `validate` gives actionable pass/fail with explicit var names (no silent failures).\n- [ ] Tool gracefully handles missing API access / auth errors.\n\n---\n\n## PM Action Items\n- Get alignment from user on the design (this spec)\n- Have Coder implement as a new tool file or submodule of existing `cowork-railway`.\n- Add a `.cargo/config` note or documentation for users to configure their Railway API key.\n"
